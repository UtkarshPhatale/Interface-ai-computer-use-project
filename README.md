# Computer-Use Automation System

A backend integration layer that gives an AI agent "hands" inside a legacy
back-office application with no API: an LLM discovers how to accomplish a
goal by driving the UI, the successful run is recorded as a typed, versioned
**capability artifact**, and that artifact is then **replayed deterministically**
(no LLM) in production, with runtime-error handling, safety guardrails, and
human escalation. See `/REPORT.md` for the original design write-up and
`/FINDINGS.md` for the day-by-day engineering log this README summarizes.

## Results

|  | Value | How it was measured |
|---|---|---|
| **Replay success rate** | 29% → **100%** after fixing two locator-matching bugs | `python3 -m dashboard.reliability` — 11 real replay runs, one non-code failure (stale session) explicitly excluded and disclosed |
| **Cost avoided per replay** | ~**$0.07/run** in LLM spend eliminated (typical case) | `python3 -m dashboard.cost_estimate` — 7 real completed discovery runs, Sonnet 4.6 public pricing |
| **Test coverage** | 10 → **22** tests, all added in response to real bugs found, not written speculatively | `python3 -m pytest tests/ -v` |
| **Generalization** | 2 structurally different target apps, 3 outcome types each (success / not-found / restricted), proven in both discovery and replay | `FINDINGS.md`, Days 5–7 |

Both metrics are generated by scripts that read real evidence under
`evidence/runs/` — they're reproducible, not quoted from memory.

## What's in this repo

| Path | What it is |
|---|---|
| `target_app/` | Proxy target #1: a legacy-flavored internal bank servicing app (Flask, table layouts, no test IDs, session auth). |
| `target_app_v2/` | Proxy target #2: a deliberately **low-accessibility** package-tracking app (div-based "buttons" with no role, unlabeled inputs) — built specifically to stress-test whether the locator fallback strategy actually works, not just exist in code. |
| `artifact/schema.py` | The capability artifact contract (typed, versioned, serializable). |
| `artifact/builder.py` | Turns a raw discovery trace into a reviewable artifact. |
| `agent/discovery.py` | The LLM-driven observe → decide → act loop (Playwright + accessibility tree + Claude). |
| `replay/engine.py` | Deterministic replay engine — the production execution path, no LLM. |
| `guardrails/policy.py` | Allowlist enforcement, risk classification, redaction. |
| `escalation/` | Human-in-the-loop intervention model, mock operator console, CLI hand-back. |
| `dashboard/` | Observability: `aggregator.py` (parses raw run logs), `report.py` (static HTML report with inline failure diagnosis), `diagnosis.py` (explains *why* a replay hard-failed), `cost_estimate.py` / `reliability.py` (the two metrics above). |
| `evidence/` | Structured run logs + screenshots (auto-generated under `evidence/runs/`) plus the curated demonstration required by the assignment. |

| `run_replay.py` | CLI: replay a saved artifact deterministically. |
| `login_session.py` | Establishes an authenticated session out-of-band against either target app (see REPORT.md — credentials never touch the artifact). |

## Running it — target_app (banking flow)

**1. Start the target app** (in its own terminal, leave it running):

```bash
python3 target_app/server.py
# -> serving on http://127.0.0.1:5055
```

**2. Establish an authenticated session** (credentials for the demo app: `operator` / `demo1234`):

```bash
python3 login_session.py --username operator --password demo1234
```

**3. Run the discovery agent on a goal** (`--headed` shows the real browser window):

```bash
python3 run_agent.py \
  --goal "Look up member 12345 and read their current savings balance" \
  --entry-url http://127.0.0.1:5055/members/search \
  --name lookup_savings_balance \
  --param member_id=12345 \
  --session .session/state.json \
  --headed
```

This prints the saved artifact path, e.g. `artifacts/cap_xxxxxxxx.json`, along
with the exact replay command.

**4. Replay the resulting artifact deterministically** (no LLM):

```bash
python3 run_replay.py \
  --artifact artifacts/cap_xxxxxxxx.json \
  --param member_id=12345 \
  --session .session/state.json \
  --headed
```

**5. See a business-outcome case handled** — replay the same artifact
with a member ID that doesn't exist:

```bash
python3 run_replay.py \
  --artifact artifacts/cap_xxxxxxxx.json \
  --param member_id=99999 \
  --session .session/state.json \
  --headed
```

You should see `status: business_outcome`, `code: MEMBER_NOT_FOUND` — not a
crash.

**6. See the human-escalation handoff.** Force it by interrupting the target
app mid-flow, or compare with `--no-escalate`. When escalation triggers:

```
[ESCALATION] Automation is stuck: <reason>
[ESCALATION] The browser window is still open at <url>.
[ESCALATION] Complete the step manually, then run:
    python -m escalation.resolve <run_id> "what you did"
```

Or start the mock operator console instead:

```bash
python3 -m escalation.console
# -> http://127.0.0.1:5099
```

## Running it — target_app_v2 (the generalization stress test)

Same flow, different app, on port 5056. Routes outside the original app's
allowlist (`/login`, `/members`, `/logout`) need `--allowed-route-prefix`:

```bash
# Terminal 1
python3 target_app_v2/server.py

# Terminal 2
python3 login_session.py \
  --login-url http://127.0.0.1:5056/login \
  --username dispatcher --password track2026

python3 run_agent.py \
  --goal "Look up package PK-1001 and read its shipment status and estimated arrival" \
  --entry-url http://127.0.0.1:5056/packages/search \
  --name lookup_package_status \
  --param package_id=PK-1001 \
  --session .session/state.json \
  --allowed-route-prefix /packages \
  --headed
```

Try `package_id=PK-0000` (not found) or `package_id=PK-9000` (on hold, a
real HTTP 403) for the other two outcome types — same command shape, replay
with `run_replay.py` the same way as above.

## Running without live services

- `artifact/schema.py`, `artifact/builder.py`, `guardrails/policy.py`, and
  `escalation/models.py` have no external dependencies and can be imported/
  tested without the target app or an LLM.
- `tests/build_sample_artifact.py` builds an artifact by hand (structurally
  identical to what discovery produces) so `replay/engine.py` can be
  exercised against the target app without any LLM calls.
- `dashboard/diagnosis.py` and `dashboard/aggregator.py` work entirely from
  files under `evidence/runs/` — no live app or LLM needed to regenerate
  the report.

Run the full test suite (no live services, no API key needed):
```bash
python3 -m pytest tests/ -v
```

## The interesting part: real bugs, found by design

`target_app_v2` was built deliberately hostile — no ARIA roles, unlabeled
inputs, div-based fake buttons — specifically to find the limits of the
role/text/xpath locator fallback strategy rather than assume it worked.
It found real ones. The two most instructive, from `FINDINGS.md`:

**A fix that didn't propagate to its sibling.** `agent/discovery.py` and
`replay/engine.py` each have their own locator-resolution logic — one drives
a live LLM loop, the other replays deterministically, so some duplication is
inherent. A substring-text-matching bug (`get_by_text("Search", exact=False)`
matching an inert "Package Search" header before the real "Search" button)
was found and fixed in discovery's version first. Running the *same* fix
through replay's independent implementation surfaced that replay still had
the identical bug — all 3 real capability artifacts hard-failed on their
first deterministic replay. This is the actual proof the "replay reproduces
what discovery found" claim needed testing, not assuming: it wasn't true
until both implementations were fixed. See `FINDINGS.md` Findings #5 and #6.

**Diagnosis staying honest as the code changes.** The observability layer's
own failure-diagnosis tool initially gave a *stale* explanation for
already-fixed historical failures once the code changed underneath it — it
kept recommending "add a self-healing pass" for failures that were actually
already fixed by a different, more specific change. Caught by re-reading the
tool's own output after a fix landed, not by a test. Fixed by having
`diagnose()` recognize the ambiguity in its own static evidence rather than
assert a single confident cause it couldn't fully prove.

Four more real findings (a null-target crash, a hardcoded guardrails
allowlist, a login script that only worked against one app's markup, and the
original missing-xpath-fallback gap) are documented in full in `FINDINGS.md`.
